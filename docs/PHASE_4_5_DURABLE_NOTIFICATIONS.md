# Phase 4.5 Durable Notifications

## Architecture

Phase 4.5 moves production-critical booking/order notification intent from the in-memory `jobQueue` into MongoDB-backed `NotificationDelivery` records. MongoDB remains the authoritative source of business state. BullMQ/Redis executes asynchronous delivery. Email providers are external side effects only.

Flow:

1. Business route/webhook updates the authoritative `Booking` or `Order`.
2. Code creates or reuses a deterministic `NotificationDelivery`.
3. The notification is enqueued to `QUEUE_NAMES.notification`.
4. `worker.js` claims and processes the notification.
5. Provider result, retry state, or failure is persisted back to MongoDB.

## NotificationDelivery

`NotificationDelivery` stores:

- `notificationKey`: unique deterministic logical identity
- `eventType`, `channel`, `template`
- target references: booking, order, modification, recipient, partner, hotel
- status: `queued`, `processing`, `retry_scheduled`, `sent`, `failed`, `reconciliation_required`, `cancelled`
- provider and provider message id
- attempts, next attempt, processing start, sent/failed times, and sanitized error fields

## Notification Keys

Keys are generated by `buildNotificationKey()` and replace unsafe random/timestamp job identities. Examples:

- `notification:booking:<bookingId>:invoice`
- `notification:booking:<bookingId>:cancelled`
- `notification:booking:<bookingId>:partner-email`
- `notification:booking:<bookingId>:admin-panel`
- `notification:order:<orderId>:invoice`
- `notification:order:<orderId>:cancelled`

Repeated triggers reuse the same delivery record.

## Queue And Worker

Queue:

- `vrindavan-sarthi-notification`

Jobs:

- `notification.delivery.send`
- `notification.recovery.sweep`

BullMQ payloads carry only `notificationDeliveryId`. The worker loads the authoritative MongoDB record.

## Claim Behavior

The worker uses an atomic `findOneAndUpdate` claim:

- `queued` or due `retry_scheduled` -> `processing`
- stale `processing` can be reclaimed
- `sent` records are skipped

This prevents normal duplicate provider sends from duplicate BullMQ delivery.

## Retry Behavior

Transient errors are retried with bounded attempts and exponential backoff using the existing Redis config defaults. Permanent errors become `failed`. Unknown provider outcomes become `reconciliation_required` rather than blindly resending forever.

## Provider Behavior

Production delivery reuses the existing Resend/SMTP email implementation. Tests may inject a fake provider through `setNotificationProvider()` and `resetNotificationProvider()`.

Where the provider returns a message id, it is stored as `providerMessageId`. SMTP/Resend provider credentials are never persisted or logged.

## Recovery

`recoverNotificationDeliveries()` can re-enqueue:

- queued records
- due retry records
- stale processing records

The recovery job is available but not enabled as a recurring scheduler by default in this phase.

## Admin Retry

Admin-only endpoints:

- `GET /api/notifications/reconciliation`
- `GET /api/notifications/:id`
- `POST /api/notifications/:id/retry`

Manual retry reuses the same `NotificationDelivery` and does not create a second logical notification.

## PartnerNotification Interaction

Admin/partner panel notifications now run through `NotificationDelivery` using `in_app` templates. The worker creates `PartnerNotification` records idempotently with an upsert. Partner scoping remains based on the existing `partnerId` model.

## Invoice Behavior

`invoiceSentAt` remains the compatibility marker and is updated only after the notification worker successfully sends or determines the invoice was already sent. Queued does not mean sent.

Invoice PDF generation remains in the existing helper and is not converted into a durable invoice artifact in Phase 4.5.

## Migrated Flows

- booking invoice/receipt
- booking cancellation email
- partner booking email alert
- admin booking email alert
- admin/partner booking panel notifications
- order invoice email
- order cancellation email
- admin order email alert
- admin order panel notification
- Razorpay webhook booking invoice trigger

## Remaining JobQueue Callers

`jobQueue.js` remains in the repository but no production-critical booking/order notification trigger should depend on it after Phase 4.5. Auth OTP/contact email flows remain synchronous/request-response and are intentionally not migrated in this phase.

## Privacy

Notification records store minimal routing and target references. They must not store provider credentials, SMTP passwords, API keys, tokens, Razorpay secrets, or MongoDB credentials.

## Deployment

API remains:

```bash
node server.js
```

Worker remains:

```bash
node worker.js
```

Production durable delivery requires Redis and a running worker. If Redis is unavailable during API handling, the MongoDB notification intent remains recoverable.

## Tests

Phase 4.5 adds:

- `tests/phase4-5-notification.foundation.js`
- `tests/phase4-5-notification.integration.test.js`

The integration test requires `PHASE_2_1_MONGO_URI` and enforces `vrindavan_sarthi_test`.

## Rollback

Because business state remains in `Booking` and `Order`, rollback can disable the worker or stop enqueuing new notification jobs without changing booking/payment/refund lifecycle state. Existing `NotificationDelivery` records remain auditable.
